# 动机与本项目的由来

> 这是一份**背景说明**：我为什么基于上游做了这些更改，改了哪些，以及为什么这样改。
> 它不属于“如何使用”的范畴，所以我把它单独放在这里，而不是塞进 README。
> 想直接上手的人只需要看 [README](../README.md)；想了解来龙去脉的人再看本文。

## 一点开场白

我自己是上游项目 [10miaomiao/bili-down-out](https://github.com/10miaomiao/bili-down-out) 的老用户，非常感激原作者把这个工具开源出来。以下说的“困难”只代表**我个人**的使用体验，**不是对上游的指责**——每个人的使用习惯不同，这里只是想诚实交代我做这些改动的出发点。

> 诚实声明：下面的“上游不能…”是基于我自己的使用场景和印象，可能与上游当前版本的实际行为有出入。如有出入，以你实际接触到的版本为准。

## 我在使用上游时遇到的三个主要困难

1. **不能“按每一次查找视频来下载”，而且下载/导出很慢**：找一个缓存往往需要反复扫描/定位，等待时间久；重新打开应用后有时又要重新来过。
2. **不能多选导出**：缓存多了之后，一次只能一个个处理，批量导出很吃力。
3. **不能按 UP 主对视频进行选择**：列表一屏平铺，没法按“哪位 UP 主的视频”来挑选，番剧和 UP 主内容还混在一起。

## 基于此，我做了哪些更改

针对上面三点，我在 fork 里做了对应的增强：

### 1. 缓解“查找/扫描慢、反复等待”→ 扫描结果持久化 + 加载状态管理

- 新增 `common/BiliAuthorRepository` 负责扫描与数据聚合，并把结果写入 `DataStore` 持久化。
- `AuthorPage` 用 `loaded` 标志位区分“已完成一次成功加载”和“空结果”，配合 `AppState` 里的扫表进度，**减少进程被杀重建后的重复全量扫描**，让首屏尽量即时可用。

### 2. 解决“不能多选”→ 导出记录多选

- 新增 `ui/page/OutListPageSelection`：用选中态集合驱动顶部“已选 N 项”的选择条，可对导出记录做**多选 + 批量操作**（删除记录、删除文件等）。

### 3. 解决“不能按 UP 主选视频”→ 按 UP 主分组视图 + 排序

- 新增按 UP 主分组的首页视图（`ui/page/DownloadListPage` / `ui/page/AuthorPage`），分组按**中文拼音排序**、带 UP 主头像。
- 番剧/影视（无 UP 主）统一归入「番剧·影视」组。
- 在分组之上提供**多维排序**：按 UP 主拼音 / 按名称 / 按大小，便于按“某位 UP 主”或“最占空间”快速挑视频。

## 为什么这样改（每个改动背后的考虑）

| 我做的更改 | 为什么 |
| :-- | :-- |
| 扫描结果做 `DataStore` 持久化 | 缓存多、重复扫描很耗时；先读缓存再加量刷新，让首屏更快，减少“一直转圈/等待”。 |
| 导出记录支持多选 | 缓存多时逐个导出太累；多选 + 批量操作更符合“一次处理一批”的真实需求。 |
| 按 UP 主分组 + 中文拼音排序 | 一屏平铺难找；分组让“想看谁的视频”一目了然，拼音排序贴合中文习惯。 |
| 番剧/影视独立成组 | 避免番剧误进“未知 UP 主”，也让 UP 主内容更干净。 |
| 多维排序（名称/大小） | 需要“按某作者”或“找出最占空间”时，能给到快速的挑选入口。 |
| 配套一批单元测试（约 1100 行） | 改动越多越需要回归保障；测试也直接说明“预期行为”，方便别人接手理解。 |

## 一句话总结

「把列表从一维平铺，升级为**先分类、可排序、可批量操作**的结构化视图，并对耗时操作做好持久化兜底」——这就是本 fork 存在的原因。
